## M2 · 手写 Agent Loop（2026-11-13）

实现位置：`scripts/agent_loop.py`、`app/tools.py`

### 1. 为什么需要步数上限

**一句话**：Agent loop 的终止条件必须由代码提供，模型的停止不可信，步数上限是防止无限调用和费用失控的唯一刹车。

**底层机制**

- Chat Completions 无状态，每一轮 `ask` 是独立的 HTTP 请求、独立计费。
- 模型每轮可能返回 `tool_calls`；本地执行后把结果回填进 `messages`，再发下一次请求。
- 模型没有「全局预算」概念，也不会因为同一个工具连续失败就自己放弃；它只能看到当前 `messages`。
- 实现：`while` 循环里维护 `steps`，每轮 `ask` 之前检查 `steps >= MAX_STEPS`，达到就停止并打印上限值。

**为什么这样设计**

- 上限计的是 **`ask` 次数**，不是工具调用次数。一次 assistant 回复可以携带多个 `tool_calls`，所以 2 步上限可能出现 4 次工具调用。
- 预算按「一条用户提问」计算：同一条提问被中断后 `--resume` 接着累计，用户发下一条消息时重新从 0 开始。
- 上限值按任务复杂度配置：简单查询 3–5；20 步任务给 20–25，留重试余量。
- 实测：19 个线索文件的串行追踪任务，19 次工具读取 + 1 次最终回答 = 20 步，`done.steps=20`，没有触发 `limit`。
- 它和「工具失败重试」是两层：重试是单次工具的失败策略，步数上限是整条链路的兜底。

**换方案会怎样**

- 不设上限：模型持续请求工具，循环不停，持续计费；递归实现还会撞 Python 默认约 1000 层的栈限制。
- 只设请求超时：单次请求的耗时不可控，超时阈值难定，且每一轮仍然计费。
- 依赖模型自觉：模型无法判断自己已经失败了多少轮，不可靠。

**容易被追问**

- 触发上限后没有最终回答怎么办？可以追加一条提示（如「已达步数上限，请基于已有信息收尾」），再做一次不传 `tools` 的请求，让模型输出总结。
- 上限设小了会怎样？合法的长任务被截断，所以要按任务复杂度给，而不是全局一个数。

### 2. 工具结果如何回填

**一句话**：手工组装 `{"role": "tool", "tool_call_id": ..., "content": ...}` 追加到 `messages`，与上一条 assistant 的 `tool_calls` 按 id 一一配对。

**底层机制**

一条完整的工具调用链路：

```text
user
assistant(tool_calls: [id=call_1, id=call_2])
tool(tool_call_id=call_1, content=结果1)
tool(tool_call_id=call_2, content=结果2)
assistant(content=最终回答)
```

- assistant 消息必须保留 `tool_calls`，包括每个调用的 `id`、`function.name`、`function.arguments`（JSON 字符串）。
- 每个 `tool_calls[].id` 必须紧跟一条 `role: tool` 消息，不能缺、不能多、不能插入其他消息。
- `content` 必须是字符串；工具返回 dict/list 时先 `json.dumps`。
- 只保留 `role`、`content`、`tool_calls` 三个字段，不把 `reasoning_content` 这类供应商私有字段写回。

**为什么这样设计**

- 协议无状态，`messages` 就是模型的全部上下文。模型「记得」工具结果，只是因为结果在 `messages` 里。
- `tool_call_id` 是多调用场景下的配对键：一次回复请求两个工具时，靠它区分哪条结果对应哪个调用。

**换方案会怎样**

- 漏掉 assistant 消息：下一条 `tool` 消息找不到配对的 `tool_calls`，接口返回 400。
- 结果塞进 `user` 消息：单工具时能跑，但丢失配对语义，多工具时模型无法对应结果与调用。
- 全量 `model_dump()` 写回：会把 `reasoning_content` 带进去，换供应商时可能 400。

### 3. 工具异常如何兜底

**一句话**：工具函数内部 `raise` 表达失败，执行层捕获后转成字符串，作为 `role: tool` 的 content 回给模型——异常不能穿透到 loop 外面。

**底层机制**

```python
try:
    result = TOOLS[name](**args)
except ValueError as e:        # 业务错误：路径越界、文件不存在
    result = f"错误：{e}"
except KeyError as e:          # 模型请求了不存在的工具名
    result = f"错误：{e}"
except TypeError as e:         # 参数与函数签名不匹配
    result = f"错误：{e}"
```

- `json.loads(call.function.arguments)` 也可能失败，同样要转成错误文本返回。
- 工具层负责「用异常表达失败」，执行层负责「把失败变成可读观测结果」，协议层负责「按 tool 消息回填」。

**为什么这样设计**

- 异常穿透到 loop：进程崩溃、会话中断，模型失去看到错误并纠正的机会。
- 工具失败本质上是模型决策的反馈信号：告诉它路径错了、工具名不存在、参数不对，它才能换一条路继续。
- 与本地 CLI 的设计一致：`git` 失败返回非零状态和 stderr，而不是让调用方崩溃。

**换方案会怎样**

- 不捕获：一个坏路径就让整个 Agent 退出，可靠性为零。
- 捕获后返回 `None`：`content` 类型不合法或模型看不出哪里错，容易继续瞎试。
- 捕获后静默重试：模型不知道失败原因，重试往往重复同一个错误。

**容易被追问**

- 工具返回内容超长怎么办？当前直接截断打印、原样回填；正式做法是截断或摘要后再进上下文，属于 M3 上下文工程。
- 工具执行有副作用（写文件）怎么防？在工具执行前加权限检查，越界写入直接拒绝，属于 M2 第三块。

### 4. 权限为什么放在工具执行前

**一句话**：模型只提交调用建议，真正执行的是本地代码；权限检查必须落在执行那一行之前，才拦得住副作用。

**底层机制**

`run_tool` 是所有工具的唯一执行入口，写操作按顺序过三层：

```text
模型返回 tool_calls
      ↓
1. ensure_safe_path(path)     硬边界：resolve + is_relative_to(ROOT) + 敏感名单
      ↓ 越界/敏感 → PermissionError，直接拒绝，不询问
2. confirm_write(path, content)  人工确认：input y/n
      ↓ 用户拒绝 → 返回「用户拒绝写入」，不执行
3. TOOLS[name](**args)        真正落盘
```

- 越界和敏感路径属于确定性危险，fail closed，不提供「放行」选项。
- 人工确认防的是「合法但非本意」：路径在项目内、文件也不敏感，但不代表人同意这次修改。
- 拒绝以普通工具结果回给模型，不抛异常；模型知道是人拒绝，就不会去找绕过路径。

**为什么这样设计**

- 模型运行在远端，碰不到本地文件系统；它返回的只是 JSON 参数，执行权完全在本地代码。
- 权限放在唯一执行入口，新增工具不会因为忘记加检查而漏掉。
- 用户拒绝必须与「环境禁止」区分：前者是人的决定，后者是系统限制，模型对两者的后续策略不同。

**换方案会怎样**

- 只在每个工具函数内部各写一套检查：新增工具容易漏，策略也无法统一。
- 只靠 system prompt 约束：模型可以无视，不构成安全边界。
- 先弹确认再做路径校验：危险路径也会弹窗，用户误点 `y` 就放行。
- 拒绝时抛异常：进程崩，模型失去换方案的机会。

**容易被追问**

- 只读工具要不要确认？不需要，但路径守卫照样要过。
- 非交互环境怎么确认？用策略文件或白名单，CI 里不能依赖 `input()`。
- 权限和沙箱的区别？权限是应用层决策，沙箱是 OS/容器层隔离，两者互补。

### 5. 事件日志为什么用 JSONL 和显式 type

**一句话**：日志是 append-only 的事件流，JSONL 保证进程被杀最多损坏最后一行，显式 `type` 区分消息事件和控制事件，恢复时再把事件投影成 `messages`。

**底层机制**

- 每行一个 JSON 对象，只追加不重写；`kill -9` 最多留下半行，读取时跳过解析失败的行即可，前面的事件不受影响。
- 事件分两类：
  - 消息事件：`user` / `assistant` / `tool`
  - 控制事件：`done` / `interrupted` / `limit`
- 写入顺序：`ask` 返回后先落 assistant 事件，再执行工具、再落 tool 事件。这样中断时日志能表达「有调用、没结果」。
- `messages_from` 只认识三类消息事件，做字段投影：`type` → `role`，丢掉 `ts`、工具事件里的 `name` 等日志专用字段。
- 控制事件承载「会话为什么结束」：`done` 表示正常完成、`interrupted` 表示被 Ctrl-C、`limit` 表示触顶。

**为什么这样设计**

- 恢复需要回答两个问题：执行到哪一步、哪些工具可能有副作用。日志必须保留控制事件，只在读侧过滤。
- 用 `type` 而不是「有没有 `role`」做判别：条件是显式的，新增事件类型不会破坏还原逻辑。
- 不用单个大 JSON 数组：追加要重写整个文件，崩溃可能全部损坏，也无法逐行 `grep` / `jq`。

**换方案会怎样**

- 只存 `messages`：丢失 `done` / `interrupted`，无法判断会话为何结束。
- SQLite / 数据库：查询更强，但多了连接、事务、迁移成本；单机实验用不上。
- pickle：不可读、跨版本脆、反序列化有代码执行风险。

**容易被追问**

- 日志会不会无限增长？按会话分文件，定期归档；生产上还需要脱敏，因为工具参数和文件内容都会进日志。
- 日志能直接当审计吗？可以，但要知道它是「意图 + 执行结果」，不是完整的系统调用记录。

### 6. kill 后如何恢复，为什么不能重放工具

**一句话**：恢复 = 从日志还原 `messages` + 用 assistant 事件数恢复步数 + 给未完成的 `tool_call` 回填「结果未知」，绝不自动重放有副作用的工具。

**底层机制**

- `pending_tool_calls(messages)`：遍历 assistant 的 `tool_calls`，凡是找不到对应 `tool_call_id` 的 tool 消息，就是中断时没跑完的调用。
- 恢复时为每个 pending 调用追加一条 tool 消息，内容是「上次执行被中断，结果未知。不要重复执行有副作用的操作。」，并把这条也写进日志。
- 回填内容明确区分「未知」和「失败」：模型可以选择先 `read_file` 核对，再决定是否重试。
- 步数用日志里 assistant 事件的数量恢复，避免反复中断重置预算。

**为什么这样设计**

- 进程可能死在「工具已经写盘」和「结果写日志」之间，单看日志无法判断副作用是否发生。
- 自动重放写操作会造成重复副作用；直接终止又会丢掉已经完成的工作。回填「结果未知」把决策权交回模型，并配合人工确认兜底。
- 合成结果必须写日志，否则下次 `--resume` 会再次命中同一个 pending，形成反复回填。

**换方案会怎样**

- 自动重放：写文件可能执行两次，日志和实际状态不一致。
- 直接把 pending 当失败：模型很可能原样重试，同样可能重复副作用。
- 不恢复步数：反复 `Ctrl-C` + `--resume` 可以无限续命，上限失去意义。

**容易被追问**

- 怎么知道写操作到底落盘没有？日志答不了，只能读文件或让工具返回可核验的结果；生产上要给写操作加幂等键或事务日志。
- 读操作也要回填「未知」吗？要，语义上同样未知，只是重放的代价低。

## M3 · 上下文工程（2026-11-18）

实现位置：`app/context.py`、`scripts/agent_loop.py`

### 7. 上下文超预算时怎么裁

**一句话**：agent loop 每轮重发全部历史，必须按「不可拆单元」从旧到新裁——先截断超长工具结果、不够再丢整轮，system 与首条 user 永不丢。

**底层机制**

- Chat Completions 无状态，每一轮 `ask` 都把全部 `messages` 重发一遍；工具结果不断累积，token 随步数近似平方增长。
- token 估算不额外请求 tokenizer：按字符数近似（中文 1 字≈1 token，英文 4 字符≈1 token），英文会被高估，方向安全。
- 单元 = `assistant(tool_calls)` + 紧随其后的全部 `tool` 消息；协议要求每个 `tool_call_id` 都有对应的 `tool` 回填，拆散直接 400。
- 决策顺序：总量超预算才动手 → 跳过 system 与首条 user → 从最旧单元开始 → 单元内超长 tool 结果先截到 2000 字符并加 `…[已截断，原长 N 字符]` → 截完达标就停，不够再整单元丢弃。
- 结果按决策表拼装，输入列表不修改；超预算事件写入 JSONL（`before` / `after`）。

**为什么这样设计**

- 不能按单条消息裁：会拆散 assistant 与 tool 的配对，请求直接失败。
- 截断优先于丢轮：工具结果是上下文里体积最大、信息密度最低的部分；保留开头通常够用，还能保住整轮对话。
- 先估算再裁剪：估算只是 `len()` 累加，裁剪要复制；预算没超时截断只会白丢信息。
- 实测：单次 `read_file` 返回 31499 字符，裁剪 `before=31752` → `after=2271`，整条任务只触发一次。

**换方案会怎样**

- 固定保留最近 N 轮：简单，但可能把任务本身滚出窗口，且 N 轮的总量不可控。
- 摘要压缩：多一次模型调用，信息损失不可逆，不适合作为兜底。
- 按条数滑动窗口：不看配对关系，必然出现孤立 `tool` 消息。
- 工具层分页（`offset` / `limit`）：最优解，让模型自己读窄范围；截断保留作最后一道保险丝。

**容易被追问**

- 估算不准怎么办？保守高估并留余量；生产上可换官方 tokenizer 或按计费接口校准。
- 截断后模型拿不到全文怎么办？标记会告诉它被截断，模型可以换更窄的调用重读；原始结果在事件日志里完整保留。
- 为什么不每轮都裁？没超预算时裁剪没有收益，只有信息损失和复制开销。

## M3 · 第一版 RAG（2026-11-20）

实现位置：`app/rag.py`、`app/retrieval.py`、`app/tools.py`

### 8. 为什么第一版检索选 BM25 + 中文 bigram

**一句话**：先建立一个零依赖、可手算、可解释的关键词基线，再决定要不要加向量检索；没有基线就无法判断 hybrid 是否真的提升。

**底层机制**

- 中文没有空格，用字符 bigram 把连续汉字切成相邻两字（`上下文` → `上下` / `下文`）；英文和数字按连续段整词保留；文档和查询共用同一个 tokenizer。
- 建倒排索引：`postings[term][chunk_id] = tf`，`df = len(postings[term])`，`dl = len(tokenize(text))`。
- 打分：`score = Σ idf(t) × tf(t,d) × (k1+1) / (tf + k1 × L(d))`，`k1=1.5`、`b=0.75`。
- 真实语料：185 块、`avgdl=212.81`、词表 11195；查询只扫 query term 命中的 postings，不遍历全部块。

**为什么这样设计**

- 旧机不装 Docker / 本地模型，BM25 只用标准库，零额外依赖。
- 分数能拆成 idf、tf、长度三项，出错时能定位是哪一项；向量相似度不可解释。
- 先拿到 recall 基线，后续加 embedding 或 hybrid 才有对比数字，而不是「感觉更准」。

**换方案会怎样**

- 直接上向量：要 embedding API 或本地模型，增加成本、延迟和不可解释性；没有关键词基线，无法证明提升来自语义而不是调参。
- 每次查询暴力遍历所有块并重新分词：O(全部块)，且文档侧分词被重复做，建索引的意义就是把它提前一次。

**容易被追问**

- 同义词怎么办？bigram 零重叠，「汽车」搜不到只写了「轿车」的块，这是 BM25 的已知缺陷，留给 hybrid。
- 单字查询为什么没结果？单个汉字切不出 bigram，首版接受；需要时可补 unigram 兜底。

### 9. tf、df、dl 分别是什么粒度

**一句话**：tf 是 `(term, chunk)` 对级，df 是 term 级，dl 是 chunk 级，N 和 avgdl 是全局；粒度混了，df 会被算成出现次数，idf 直接失真。

**底层机制**

| 数据 | 粒度 | 来源 |
|---|---|---|
| tf | `(term, chunk)` 对 | `postings[term][chunk_id]` |
| df | term | `len(postings[term])` |
| dl | chunk | `len(tokenize(chunk["text"]))`，含重复 |
| N | 全局 | 过滤后 `len(chunks)` |
| avgdl | 全局 | `sum(doc_len.values()) / N` |

- df 统计的是「有多少块包含这个 term」，同一块里出现多次只算一次。
- dl 统计的是块内 term 总数，重复词也计入长度；重复程度由 tf 单独表达。
- N、avgdl、postings、doc_len 必须基于同一个过滤后的集合；空 term 块不能只从 postings 里消失、却还留在 N 里。

**为什么这样设计**

- BM25 的三个因子各需要不同粒度的数据：idf 要 df，tf 因子要 tf，长度归一化要 dl 和 avgdl。
- 把 df 算成 `sum(tf)` 会让 df 可能大于 N，idf 公式失真甚至失去意义。
- 用字符长度代替 dl 会让中英文密度不同的块被错误归一化。

**换方案会怎样**

- 只存 tf 不存 chunk 维度：不知道哪个块命中，无法打分。
- 把 df 和 tf 都放 term 级：df 可以，tf 不行；tf 必须能按块取。
- 每次查询现算 avgdl：结果正确，但每次多一次 O(N) 遍历，属于重复计算。

**容易被追问**

- df 要不要单独存？`len(postings[term])` 是 O(1)，不必；存了也只是缓存。
- 空块为什么要过滤？它不贡献任何 term，却会拉低 avgdl、放大 N，影响所有分数。

### 10. 引用与排序为什么都要确定性

**一句话**：检索结果必须带 `path` 和行号，agent 的回答才能被核验；排序必须分数降序、同分按唯一 id 升序，否则测试和评测都不可复现。

**底层机制**

- chunk id 形如 `path:start-end#n`，其中 `#n` 是文档内序号，解决同一行被切多块时 id 冲突。
- `search` 返回 `id`、`path`、`start_line`、`end_line`、`text`、`score`。
- 排序键是 `(-score, chunk_id)`：负号把分数降序转成负分升序，第二键保证同分时按 id 升序。
- query term 用 `set` 去重，`set` 的迭代顺序受字符串哈希随机化影响，跨进程可能不同。

**为什么这样设计**

- 引用让回答可核验：用户能回到原文，模型也更难编造。
- 同分时 BM25 不提供先后；不指定 tie-breaker，顺序由 `scores` 插入顺序决定，而插入顺序又受 `set` 顺序影响，结果会跨进程漂移。
- 漂移的后果：测试间歇性失败、评测集 top-k 对比误判、日志无法复现。

**换方案会怎样**

- 只返回文本：用户无法定位来源，引用准确率无法测。
- 用 `reverse=True`：同分时 id 也变降序，仍然依赖输入顺序，不能保证稳定。
- 同分不排序：结果「能用」，但不可复现，工程上不可接受。

**容易被追问**

- 行号区间会重叠吗？会，切块有重叠；id 的 `#n` 保证唯一，行号用于引用而不是去重。
- 引用准确率怎么测？30 条评测集，检查回答引用的区间与 ground truth 是否相交。

## 口述版（每条 30 秒）

1. **步数上限**：模型不会自己停，每轮都是独立计费的 HTTP 请求。循环里计数 `ask` 次数，到上限就停。它计的是轮数不是工具数，一次回复可以带多个工具调用；预算按一条用户提问算，恢复时接着累计。代价是长任务可能被截断，所以上限按任务复杂度给。实测 19 次读取加一次收尾正好 20 步。
2. **工具回填**：协议无状态，上下文全靠 `messages`。assistant 的 `tool_calls` 要原样带上，然后为每个 `tool_call_id` 追加一条 `role: tool` 的消息，结果必须是字符串，按 id 一一配对，顺序不能乱。
3. **异常兜底**：工具内部 `raise`，执行层 `except` 接住转成错误文本，作为 tool 结果回填。不能让异常穿透，否则进程崩、模型也没机会换路径。要覆盖业务错误、工具名不存在、参数不匹配和 JSON 解析失败四类。
4. **权限层**：模型只给建议，执行权在本地。所有工具走 `run_tool` 一个入口，写操作先过路径守卫（越界直接拒，不询问），再人工确认；拒绝作为普通工具结果回给模型。顺序不能反，否则危险路径也会弹窗。
5. **事件日志**：每行一个 JSON，append-only；进程被杀最多坏最后一行，读取时跳过。事件分消息事件（user/assistant/tool）和控制事件（done/interrupted/limit），用显式 type 判别；恢复时只把三类消息投影成 messages，type 换成 role，丢掉日志专用字段。
6. **kill 恢复**：从日志还原 messages，用 assistant 事件数恢复步数；对「有调用没结果」的 tool_call 回填「结果未知」而不是重放，因为写操作可能已经落盘。回填也要写日志，否则下次恢复会重复命中。
7. **上下文裁剪**：每轮都重发全部历史，token 会平方级增长。按「assistant + 它的 tool 回填」为单元从旧到新裁，不能拆配对；先截断超长工具结果，不够再丢整轮，system 和首条 user 永不丢。实测 31k 字符的工具结果裁到 2.2k，整条任务只触发一次。真正的解法是工具层分页，截断只是保险丝。
8. **BM25 基线**：第一版用 BM25 + 中文 bigram，零依赖、可手算、可解释。倒排索引是 term 到 `{chunk: tf}`，查询只扫命中 term 的 postings，不遍历全部块。先拿到 recall 基线，后面加向量或 hybrid 才有对比数字。已知缺陷是同义词零重叠。
9. **统计量粒度**：tf 是 `(term, chunk)` 对级，df 是 term 级，dl 是 chunk 级，N 和 avgdl 是全局。df 用 `len(postings[term])`，不是 tf 求和；dl 是 token 数，不是字符数；这些数据必须基于同一个过滤后的集合，否则 idf 和长度归一化都会失真。
10. **引用与确定性**：检索结果带 path 和行号，回答才能被核验。排序分数降序、同分按唯一 id 升序；query term 用 set 去重，而 set 的迭代顺序受哈希随机化影响，不加 tie-breaker 同分顺序会跨进程漂移，测试和评测都不可复现。
